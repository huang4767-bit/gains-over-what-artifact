# Code note: forecast-horizon covariates in CastFSR

This file documents what the public CastFSR code does with forecast-horizon covariates and how this compares with the descriptions in arXiv 2608.03031 v1, v2 and v3 (2026-11-13).

Source: `https://github.com/Xiaoyu-Tao/CastFSR`, commit `def273e0be9df1cea3e9302189c4ed9eecee5af4` (latest on main, 2026-08-03, "Update result figures"). The source files were downloaded from raw.githubusercontent.com by commit id and read line by line. They were not run. Line numbers are those of the downloaded files.
Paper: HTML sources of arXiv 2608.03031 v1, v2 and v3, extracted verbatim.

## 1. Code: the LLM prompt contains the complete covariates of the forecast horizon

- `recipe/time_series_forecast/forecast_context_v3.py`
  - For each dataset, `future_known_covariates` and `historical_covariates` are the same: ETTh1/ETTh2/ETTm1/ETTm2 L55-56, L99-100, L139-140, L181-182 (HUFL ... LULL, measured loads); Wind L228-229 (includes `ture_w_speed`, which A.1 of the paper calls "observed wind speed"); NP L268-269; PJM L304-305; BE L342-343; DE L382-383; FR L420-421 (for electricity prices, all five markets use day-ahead forecasts).
  - `render_exogenous_snapshot` (L1024-1067): writes "Future exogenous variables are provided and visible." (L1027); gives per variable the mean, minimum, maximum and first-to-last change over the forecast horizon (L1038-1042); and puts the "Complete future-window exogenous matrix" into the prompt as a CSV, hour by hour (L1050-1066).
  - `build_situation_information` (L1070-1131): raises the error "Complete future exogenous variables are required" if the forecast-horizon covariates are incomplete (L1089-1092). The block is placed in the prompt under the heading "Exogenous-variable information (target-blind)" (L1127-1128).
- `recipe/time_series_forecast/teacher_agent_flow_v3.py` L103-113, L162-173: the user prompt at each step carries the block above.
- `recipe/time_series_forecast/utils.py` L95-127, L154-158: when the numeric forecaster is called, the request always carries the forecast-horizon covariates ("mandatory target-free future-covariate payload").
- `recipe/time_series_forecast/model_server.py` L203-264: when covariates are present, Chronos-2 uses `predict_df(..., future_df=...)`, so the forecast-horizon covariates are fed to Chronos-2. **Of the five experts, only Chronos-2 actually uses forecast-horizon covariates.** DLinear, PatchTST and iTransformer concatenate only the history (L162-171), and ARIMA uses only the target (L174-182).
- `forecast_context_v3.py` L3-5, module summary: "The experiment contract exposes every non-target covariate over the complete forecast horizon." L705-713 take values from the raw CSV by forecast-horizon timestamp. L244 labels `ture_w_speed` as "visible over the complete horizon in this experiment". `future_forbidden_covariates` (L28) is a dead field with no switch that turns it on.
- Base class `time_series_forecast_agent`: the LLM prompt has no forecast-horizon covariates, but `predict()` (L2259-2264) attaches them in the same way, and Chronos-2 receives them if it is selected.
- Which agent flow the paper used cannot be determined from the repository (the flow name comes from the `agent_name` field of the samples, and there are no launch scripts or data preparation scripts). Circumstantial evidence points to the v3 flow: v3 C.4 "The situation and covariate block is cached within a run" matches the caching in `teacher_agent_flow_v3.py` L96-113, which the base class does not have; v3 C.3 "released Wind guard bounds are [-2,102]" matches L230; the prompt templates quoted in v1/v2 are identical to `teacher_prompts_v3.py` L76-78. The repository has only 3 commits, all on 2026-08-03, before v1.
- `README.md`: the slow-thinking stage "Uses future-known contextual variables, such as calendar effects, weather conditions, external events, and exogenous features"; the wind case "uses future meteorological context to correct an overly deep midday trough".

## 2. Paper: the v3 description differs from v1/v2 and from the code

- v1, v2 (verbatim): "Each prompt contains the shared forecasting situation, including task metadata, domain priors, timestamp scope, sampling frequency, target variable, and available future-known covariates." and "All decisions remain target-blind, grounded in historical observations, ... available future-known covariates, diagnostic evidence, and auxiliary forecasts."
- v3 (2026-11-08, verbatim): "Only information available at the forecast origin is used, excluding forecast-horizon target and covariate values." (3.1); "To prevent information leakage, policy inputs are restricted to historical target observations and covariates, excluding forecast-horizon target and covariate values." (4.1.3)
- The sharpest sentence is in v3 3.3: "All evaluated expert calls, including Chronos-2, use historical target observations and historical covariates according to their input interfaces." This contradicts `model_server.py` L203-257 directly. v3 has at least 7 places (the slow-thinking paragraph in 3.3, Figure 5, C.3, Template 1, C.4 and others) that say forecast-horizon covariates are excluded. No place in the text acknowledges their use.
- Wind case: v1 "shows deviations under future wind-speed changes, motivating contextual reasoning"; v3 changes this to "motivating an assessment against historical wind and target evidence". The electricity-price evaluation protocol (specific dates, 60 windows, training-segment sigma) was written into v3 only, with unchanged numbers.
- The numbers of Table 1 are nearly the same across v1, v2 and v3. In the CastFSR rows only two values changed by 0.001 in the third decimal: ETTh1 Zero MSE (0.081 -> 0.080) and ETTm2 Zero MAE (0.238 -> 0.237). **The text changed the protocol description, and there is no sign that the numbers were rerun.**

## 3. Implications (cautious wording)

- Wording: **"in the `def273e` version of the public code"**, both the LLM and the Chronos-2 expert receive forecast-horizon covariates, and the description in the v3 text disagrees with this. No inference is drawn about which version of the code produced the numbers in the paper. The correct term is "inconsistency".
- Classification: the consistency between the paper text and the code is a document-level fact that can be checked. Test isolation on ETT and Wind is conditional: if the reported numbers came from the public code path, then information from the test period enters the input. It is not counted as a confirmed problem.
- Electricity prices: the covariates are day-ahead forecasts, available at forecast time, so this is **not leakage**. It is only an inconsistency with the v3 text.
- ETT: HUFL and the other covariates are measured loads, and the measured values of the forecast horizon are not available at forecast time. Wind: `ture_w_speed` is the measured wind speed, and wind power output is mainly determined by wind speed. **If the numbers in the paper came from this code path, then on ETT and Wind, information from the test period enters the input.** This is the same kind of finding as for MemCast on ETTh, where realised covariate values over the next 96 steps are given (see `electricity/memcast/`).
- Table 3, wind: removing slow thinking gives 2.310, and the full system gives 1.596, the largest improvement in the table. The slow-thinking stage is the stage that reads the forecast-horizon covariates. This is only a correlation and supports no causal conclusion.
- A way to test this on Wind: a diagnostic that fits a power curve with only the same-time `ture_w_speed` and checks whether its z-MSE gets close to or better than the 1.596 of CastFSR and the Table 1 baselines. See `electricity/wind_diagnostic/`.
- To be checked: (a) whether the individual baselines in Table 1 of the paper (Chronos-2 and others) received the forecast-horizon covariates; (b) whether `ture_w_speed` in Wind is the same-time measured value (TFB dataset description).
